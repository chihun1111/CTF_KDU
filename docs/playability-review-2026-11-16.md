# 참가자 관점 진행성 검토 — 2026-11-16

**상태: 브라우저 CI 결과를 추가하기 전의 초안.**

검토 기준 커밋: `9da60cbef398665e097734f9d6987e1aaf0e8605`.

## 판단 요약

**공개 응답으로 확인한 01~06은 소스 보기와 URL 탐색을 아는 참가자가 진행하기 쉬운 편이다.** 01·03·04·05·06은 외부 풀이 힌트 없이 플래그를 획득했고, 02는 경로에 관한 환경 문의 후 다른 해석을 시도해 획득했다. 07·08은 자동 안전 검토에 따라 독립 풀이가 중단되어 정상 사용 흐름만 확인했다. 따라서 이 결과로 “8개 모두 초심자가 쉽게 완주한다”고 판단할 수는 없다.

진행을 개선할 때 우선 볼 부분은 다음과 같다.

1. **부분 확인과 최종 완료의 관계를 명확히 안내한다.** 추가 코드 검토에서는 입력이 폼의 상태에만 보관되고, 진행 표시는 최신 제출 1회 기준이며, 최종 완료에는 한 요청에 8개가 모두 필요했다. 참가자가 부분 정답이 계속 누적된다고 이해하면 나중에 다시 입력해야 하는 상황이 생길 수 있다. 브라우저에서의 재현은 보류 중이다.
2. **02의 “루트” 표현을 서비스 기준 경로로 명확히 한다.** 실제 검토에서 도메인 루트와 서비스 기본 경로를 다르게 해석해 추가 문의와 탐색이 발생했다.
3. **첫 행동을 모르는 참가자도 힌트를 찾을 수 있게 한다.** 01·04·05는 소스 탐색을 떠올리면 쉽지만, 표시 본문만으로는 첫 행동이 잘 드러나지 않는다. 허브의 힌트 링크도 현재 코드상 “운영 공지”, 도착 화면 제목은 “공개 안내”다.
4. **04~06의 학습 목표와 난도 표기를 실제 경로에 맞춘다.** 세 문제는 연결된 공개 파일을 한 번 여는 것으로 획득할 수 있었다. 특히 04의 저장소 조작, 06의 소스맵 이해는 정답 획득만으로 학습 여부를 확인하기 어렵다.
5. **07·08의 정상 화면에서 생기는 혼동을 줄인다.** 07은 목록 집계·제목 링크·복귀 동선, 08은 수령/금고 용어와 실패 후 재시도 안내를 보완할 여지가 있다.

이 문서는 풀이 진행에 관한 관찰과 개선안을 기록한다. 문제 풀이 로직과 채점 정책은 변경하지 않았고, 재현용 브라우저 검사와 실행 문서를 추가했다. 정답 원문, 공격 페이로드, 임시 플래그 값은 포함하지 않는다.

## 검토 방법과 결과의 한계

세 검토자가 01~03, 04~06, 07~08을 나누어 먼저 독립적으로 검토했다. 그 단계에서는 서버 구현, 기존 풀이, 기존 보고서, 테스트 구현과 요청 도구 내부를 읽지 않았다. 실제 문제 서버의 공개 HTTP 응답과 그 안에서 발견한 자산을 사용했으며, 인증 및 개인별 플래그 공급 부분은 fixture backend가 제공하는 환경이었다.

독립 관찰을 마친 뒤에만 [공식 힌트 정의](../apps/backend/src/hints/hint-definitions.ts), [README](../README.md), 기존 보강 보고서 및 일부 플랫폼 코드를 대조했다. 아래에서는 다음 세 근거를 구분한다.

| 근거 종류 | 확인한 것 | 이 근거만으로 확인하지 못하는 것 |
| --- | --- | --- |
| 독립 HTTP 관찰 | 최초 응답, 공개 단서, 실제 수행한 요청, 응답에 포함된 플래그 또는 정상 결과 | 화면 렌더링, 마우스·키보드 조작, 실제 제출 승인 |
| 관찰 후 코드·문서 대조 | 공식 힌트 내용과 시점 표기, 제출·진행 표시의 구현 계약 | 실제 배포에서의 UI 동작, 힌트의 실제 공개 시각 |
| 기존 회귀 검증 기록 | 기존 문서가 기록한 구현 및 의도된 풀이 경로의 검증 범위 | 구현을 모르는 참가자가 단서를 발견하는 난이도 |

로컬 Chromium 제약으로 독립 검토는 HTTP·공개 자산 분석이었다. 응답 전문을 직접 읽는 방식은 특히 01에서 일반 참가자의 화면보다 HTML 주석에 접근하기 쉽다. 평가자는 웹 보안의 기본 개념을 아는 검토자이며, 실제 학생을 모집해 관찰한 결과가 아니다. **HTTP 요청 수를 사람의 풀이 시간, 실제 초심자 성공률, 운영 환경의 성능으로 환산하지 않는다.**

02의 환경 문의는 별도 개입으로 기록했다. 정답 경로나 페이로드를 받지는 않았지만, 환경 문의 후 다른 공개 경로 해석을 시도하라는 안내가 있었으므로 엄격한 무보조 성공으로 합산하지 않는다.

07·08은 자동 안전 검토로 독립 풀이 진행이 중단되었다. 이후에는 정상 화면과 기본 동작만 확인했다. 07에서 범위 변경 전 수행한 비정상 문자 검색 1회는 일반 오류를 관찰한 것으로만 기록하며 취약점 확인이나 풀이 성공의 근거로 사용하지 않는다. 이 중단은 참가자가 문제를 풀다가 막혔다는 관찰과도 구별한다.

## 문제별 확인 범위

“획득”은 문제 응답에서 플래그를 확보했다는 뜻이다. 플랫폼 제출·정답 승인·클리어 인증까지 완료했다는 의미는 아니다.

| 번호 | 문제 | 이번 결과 | 실제 HTTP 요청 | 참가자 관점 판단 |
| --- | --- | --- | ---: | --- |
| 01 | 캠퍼스 축제 안내 | 무보조 획득 | 1 | 쉬움. 소스 보기가 첫 관문이다. |
| 02 | 서비스 상태 | 환경 문의 후 획득 | 6 | 보통. 공개 단서의 경로 기준이 모호했다. |
| 03 | 과제 제출 확인 | 무보조 획득 | 5 | 쉬움. 변경한 조회의 결과가 다음 행동을 뒷받침한다. |
| 04 | 동아리 운영 현황 | 무보조 획득 | 2 | 쉬움. 공개 자산 읽기만으로도 획득한다. |
| 05 | 동아리 홍보 페이지 | 무보조 획득 | 2 | 쉬움. 연결 자산이 짧고 단서가 눈에 띈다. |
| 06 | 빌드 자료 보관함 | 무보조 획득 | 획득 2 + 형식 확인 1 | 쉬움. 화면에 공개 파일의 직접 링크가 있다. |
| 07 | 자유게시판 검색 | 정상 UX만 확인 | 정상 5 + 범위 변경 전 1 | 풀이 난도 판정 보류. 정상 검색은 단순하다. |
| 08 | 특별상 수령 안내 | 최초 화면·기본 거부 흐름 확인 | 2 | 풀이 난도 판정 보류. 다음 조사 방향은 약하다. |

공통 서비스 목록 확인 1회를 포함해 **검토 전체 요청은 28회**다. 06의 추가 1회는 이미 확보한 공개 JSON의 형식 확인이다. 독립 검토에서 공식 단계별 힌트를 사용한 문제는 없었으며, 이후의 힌트 평가는 내용 대조다.

### 01 — 첫 성공을 만들기 좋지만 도구 사용의 문턱이 있다

표시 본문은 축제 일정과 부스 안내다. 입력창이나 별도 조사 링크가 거의 없고, 응답 문서에는 화면에 표시되지 않는 정보가 있다. 소스 확인을 시작하면 추가 경로 탐색이나 해독이 필요하지 않아 입문 문제로 간결하다.

소스 보기 자체를 모르는 참가자에게는 행사 날짜나 학과명에서 암호를 찾는 불필요한 추측이 생길 수 있다. 공통 참가 안내에서 소스 보기와 개발자 도구를 여는 방법을 소개하거나, 첫 단계 힌트를 쉽게 찾게 하면 도움이 된다. 정답 위치를 서비스 본문에 직접 적을 필요는 없다.

### 02 — 실제로 추가 해석이 필요했던 지점

공개 JavaScript에 “운영 규칙 문서는 루트의 표준 파일을 참고하세요.”라는 안내가 있었다. 검토자는 이를 도메인의 루트로 해석해 표준 규칙 파일을 요청했고, 테스트 환경의 공통 경로 응답을 받았다. 환경 문의 후 “루트”를 현재 서비스의 기본 경로로 다시 해석했을 때 다음 공개 단서를 찾았다.

이는 단순한 실패 횟수보다 **참가자가 어떤 경로 기준을 의도했는지 추정해야 했다는 점**이 중요하다. 실제 배포의 도메인 루트가 무엇을 반환하는지는 브라우저 CI에서 확인해야 한다. 테스트 환경의 404를 그대로 제품 결함으로 기록하지 않는다.

문구를 “이 상태 서비스의 기본 경로 아래에 공개된 운영 규칙 파일을 참고하세요.”처럼 바꾸면 조사할 파일의 개념은 유지하면서 경로 기준의 혼동을 줄일 수 있다. 공식 힌트도 파일 종류와 다음 기능을 안내하지만 이 기준 경로의 모호함을 직접 해소하지는 않는다.

### 03 — 가설에 대한 중간 피드백이 좋다

목록의 정상 상세를 확인하면 번호로 항목을 구분한다는 구조와 소유자가 보인다. 번호를 바꾸어 조회했을 때 다른 소유자의 항목이 표시되어 가설이 맞다는 피드백을 얻었고, 긴 후보 범위를 탐색하지 않고 획득했다.

URL의 매개변수를 읽고 바꿀 수 있다는 기초가 있으면 진행하기 쉽다. 소유자 표시는 접근 범위가 달라졌음을 이해하게 하므로 유지할 가치가 있다. “전체 과제”가 개인 목록의 총계라는 점을 더 명확히 하면 목록 밖 항목을 조사하는 행위와 화면 집계가 충돌해 보이는 정도도 줄일 수 있다.

### 04 — 획득과 저장소 조작 학습을 구별해야 한다

공개 HTML에서 연결된 짧은 자산을 확인하는 것만으로 플래그를 확보했다. 그 자산에는 브라우저에 저장된 상태에 따라 화면을 바꾸는 로직이 있었지만, 실제 획득에 저장소 변경은 필요하지 않았다.

따라서 정답 제출만으로 참가자가 브라우저 저장소와 권한 판정을 이해했다고 판단하기 어렵다. 학습 목표를 강조하려면 해설이나 선택형 학습 확인에서 “저장된 상태를 바꾼 뒤 화면이 어떻게 달라지는지”를 설명하게 하는 방법이 있다. 난독화로 읽기를 막는 방향의 난도 상승은 이번 관찰만으로 권하지 않는다.

공개 코드상 상태 판정은 초기화 때 실행되므로 저장소 변경 후 다시 불러오는 단계가 중요해 보였다. 실제 브라우저에서 패널이 바뀌는지는 별도 확인 항목이다.

### 05·06 — 짧은 연속 학습에 적합하며 난도 상승은 약하다

05는 연결된 공개 자산이 짧고, 06은 자체 화면에서 공개 파일로 바로 이동할 수 있었다. 06의 파일을 읽어 획득하는 데 별도 복원 도구나 복잡한 경로 추측은 필요하지 않았다. 파일의 개념을 처음 소개하는 문제로는 부담이 작다.

05의 자산은 06의 공개 자료로 이어진다. 연속 학습 관계를 설명하면 두 자료가 연결된 이유를 이해하기 쉽다. 반면 06 공식 1차 힌트는 05의 자산으로 돌아가도록 안내해, 06에서 독립적으로 시작한 참가자에게 현재 화면의 직접 링크보다 돌아가는 경로가 될 수 있다. 첫 힌트는 현재 보관함의 공개 파일을 관찰하도록 하고, 문제 간 연결은 해설에서 보충하는 방법을 검토할 수 있다.

처음 독립 검토에서는 두 문제의 값을 연속해서 발견할 때 제출 대상을 혼동할 가능성을 제기했다. 후속 코드 대조에서는 서버가 실제 일치 항목을 찾아 판정하고, 폼에도 입력 칸 위치와 문제 번호가 달라도 된다는 안내가 있음을 확인했다. 따라서 **칸 위치를 잘못 고르는 것이 곧 제출 실패라는 문제는 확인되지 않았다.** 이 안내가 실제 화면에서 잘 읽히는지는 브라우저 확인 사항이다. 근거는 [제출 폼](../apps/frontend/app/components/final-submit-form.tsx)과 [최종 제출 서비스](../apps/backend/src/submissions/final-submit.service.ts)다.

### 07 — 정상 검색은 명확하나 목록과 복귀 동선을 다듬을 수 있다

정상 검색어, 결과가 없는 검색어, 빈 검색의 결과가 구분되었다. 입력 목적이 가까이 설명되고 검색어도 결과 화면에 유지된다. 다음은 실제 정상 응답에서 관찰한 혼동 지점이다.

- 첫 화면의 “총 3건”과 빈 검색 결과의 4건이 다르다. 최근 일부만 표시하는 설계라면 “최근 3건 표시”처럼 집계 범위를 밝히는 편이 명확하다.
- 제목 링크는 상세 글 대신 해당 제목을 검색한 결과로 이동한다. “이 제목으로 검색”처럼 행동의 의미를 표시하면 본문이나 첨부를 찾아 같은 경로를 반복하는 일을 줄일 수 있다.
- 정상 검색 결과에는 게시판 첫 화면으로 돌아가는 로컬 링크가 없다. 오류 화면에는 복귀 링크가 있으므로 정상 결과에도 같은 동선을 제공할 수 있다.
- 좁은 화면에서 표 내부의 가로 스크롤을 사용하도록 CSS가 작성되어 있다. 가려진 열의 존재와 스크롤 방법을 참가자가 알아볼 수 있는지는 실제 화면 확인이 필요하다.

이 항목들은 정상 사용성 평가다. 실제 취약점 풀이의 성립 여부나 난도는 평가하지 않았다.

### 08 — 거부 이유는 보이지만 조사 방향과 재시도 규칙이 약하다

최초 화면에는 수령자와 권한의 기본 상태가 표시되고, 제공된 확인 동작은 권한 부족을 설명하는 거부 화면으로 이어졌다. 실패 화면에는 돌아가는 링크가 있다.

서비스 화면만으로는 티켓을 어디서 관찰해야 하는지, 어떤 목표를 향해 조사해야 하는지 이해하기 어렵다. 고급 보너스 문제의 의도일 수 있으므로 기본 관찰 도구 안내와 심화 풀이 힌트를 분리해 제공하는 방식이 적절하다. 구체적인 풀이를 이 문서에서 제안하지 않는다.

“특별상 수령”, “티켓 확인”, “금고 열기”가 함께 사용되어 결과 화면의 표현을 통일할 여지가 있다. 또한 “한 번만 사용할 수 있다”는 문구에 확인 실패와 최종 수령의 관계가 설명되지 않아, 참가자가 첫 시도를 주저할 수 있다. 실제 소모 시점을 확인한 뒤 실패 후 재시도 가능 여부를 사실에 맞게 안내해야 한다.

요청 도구의 허용된 인터페이스만으로 발급된 티켓 쿠키가 다음 요청까지 그대로 보존되는지는 확정하지 못했다. 기본 거부 응답을 특정 티켓의 검증·재사용·무결성을 입증하는 검사로 해석하지 않는다.

## 전체 난도 흐름과 공식 힌트

[README](../README.md)는 하 2개·중 4개·중상 2개 및 기초·응용·심화의 단계적 학습을 설명한다. 이번 관찰에서는 02의 경로 해석보다 04~06의 공개 파일 읽기가 간단했다. 따라서 번호가 커질수록 계속 어려워지는 곡선으로 보기는 어렵다.

쉬운 문제를 여러 개 두는 것은 첫 성취와 반복 학습에 유용할 수 있다. 다만 03~06을 모두 비슷한 “중” 단계로 기대하게 하기보다는, 각 단계의 초점을 “조회 범위 관찰”, “브라우저 상태”, “배포 자산”, “공개 빌드 자료”처럼 학습 목표로 설명하는 편이 실제 경험과 잘 맞는다. 07·08에서 요구하는 지식이 넓어진다는 점은 공식 힌트의 내용으로 추정할 수 있지만, 독립 완주 결과가 없어 난도 상승의 크기는 판정하지 않는다.

### 공식 시점 표기

아래는 [힌트 정의의 `releaseTiming`](../apps/backend/src/hints/hint-definitions.ts)에 적힌 운영 시점이다. 해당 시각의 예약 자동 공개 또는 실제 공개 완료를 검증한 표가 아니다. 현재 [힌트 화면](../apps/frontend/app/hints/page.tsx)은 운영자가 공개한 단계가 표시된다고 안내한다.

| 문제 묶음 | 1차 힌트 | 2차 힌트 | 추가 운영 힌트 |
| --- | --- | --- | --- |
| 01·02 | 시작 +60분 | 시작 +120분 | 종료 -60분 |
| 03~06 | 시작 +120분 | 시작 +180분 | 종료 -60분 |
| 07·08 | 시작 +180분 | 시작 +240분 | 종료 -60분 |

01과 04처럼 표시 본문에서 첫 행동을 찾기 어려운 문제에서는, 도구 사용법을 모르는 참가자가 첫 방향 안내까지 오래 대기할 가능성이 있다. 이는 실제 학생의 막힘 시간을 측정한 결론이 아니며, 예정 시점과 첫 행동의 요구 지식 사이에서 확인한 운영 위험이다. 기본 도구 안내를 시작 시점에 제공하고, 문제별 핵심 힌트는 현재의 단계적 공개를 유지하는 방식으로 구분할 수 있다.

대회 길이도 먼저 정해야 한다. 예를 들어 4시간 대회에 현재 표기를 적용하면 07·08의 2차 힌트는 종료 시각, 공통 추가 힌트는 그보다 1시간 앞이 된다. 5시간 대회에서는 07·08의 2차와 추가 힌트가 같은 시점이다. 실제 일정이 정해지기 전에는 단계 순서와 학습 시간을 확보했다고 판단하기 어렵다.

### 내용의 단계성

| 대상 | 공식 힌트와 관찰의 관계 | 조정 제안 |
| --- | --- | --- |
| 01 | 문서 관찰에서 구체적인 흔적으로 좁혀 가는 흐름이 일관적이다. | 첫 도구 사용법을 공통 안내에서 보완한다. |
| 02 | 공개 규칙 파일과 다음 기능은 안내하지만 서비스 기준 경로는 명확하지 않다. | 본문 단서와 힌트에서 같은 기준 경로 표현을 사용한다. |
| 03 | 번호의 의미에서 조회 범위로 좁혀 간다. 실제 중간 응답의 피드백과 잘 맞는다. | 소유자와 개인 목록의 의미를 유지한다. |
| 04 | 브라우저 판정, 저장된 값, 조작 후 재확인의 순서가 일관적이다. | 획득만으로 조작을 학습했다고 평가하지 않는다. |

| 07·08 | 뒤 단계로 갈수록 요구 개념이 구체화된다. | 완주 검토 전에는 충분성이나 실제 난도를 확정하지 않는다. |

### 힌트를 찾는 동선

[허브 코드](../apps/frontend/app/hub/page.tsx)에서 힌트 이동 링크는 “운영 공지”이고, [도착 화면](../apps/frontend/app/hints/page.tsx)의 제목은 “공개 안내”다. “힌트”를 찾는 참가자가 링크를 즉시 알아보기 어려울 수 있다. “힌트·운영 공지” 또는 “공개 힌트”처럼 기능 이름을 포함하면 선택의 의미가 명확해진다. 화면에서 실제로 얼마나 발견하기 어려운지는 브라우저 및 학생 관찰로 확인할 사항이다.

## 추가 코드 관찰: 제출의 진행 표시와 입력 보존

이 절은 독립 풀이가 끝난 뒤 코드를 대조한 결과다. 실제 브라우저에서의 재현 결과로 표현하지 않는다.

| 확인한 구현 | 참가자에게 생길 수 있는 해석 차이 | 근거 |
| --- | --- | --- |
| 플래그 입력은 빈 값으로 초기화되는 컴포넌트 상태다. 이 폼에는 재방문 시 입력을 복원하는 지속 저장이 없다. | 새로고침하거나 다른 문제를 보러 갔다가 폼이 다시 만들어지면 이전 입력이 남아 있을 것으로 기대할 수 있다. | [제출 폼](../apps/frontend/app/components/final-submit-form.tsx) |

| 폼은 일부만 먼저 확인할 수 있다고 안내하고 버튼은 “최종 제출”이다. | 부분 확인과 전체 완료의 차이를 한 번 더 해석해야 한다. | [제출 폼](../apps/frontend/app/components/final-submit-form.tsx) |

우선은 구현 계약을 짧고 명확하게 설명하는 것이 좋다. 예를 들어 다음 안내를 실제 동작과 맞춰 검토할 수 있다.

> 부분 확인 결과는 최근 제출 기준입니다. 페이지를 새로고침하거나 떠나면 입력 내용이 사라질 수 있습니다. 최종 완료하려면 모아 둔 8개 값을 한 번에 제출하세요.

“최근 제출 결과”라는 현재 제목은 정확한 방향이다. 같은 화면의 “현재 확인된 항목”과 결과 메시지도 누적 여부가 일관되게 읽히도록 맞추는 것이 좋다. 탐색 중 입력 보존이나 누적 진행 표시를 추가할지는 운영 방식을 정한 뒤 별도 설계할 수 있다. 이번 검토에서는 구현을 바꾸지 않았다.

## 브라우저 검증: 보류

**이 초안에는 성공한 브라우저 실행 기록이나 스크린샷 근거를 아직 추가하지 않았다.** 이후 실행 결과를 아래 항목에 대응시켜 기록해야 한다. HTTP 응답이 정상이라는 이유로 이 항목을 통과 처리하지 않는다.

## 기존 구현 회귀검사와의 관계

[1차 보강 보고서](review-2026-11-16.md)와 [후속 보강 보고서](review-followup-2026-11-16.md)는 전체 서비스, 사용자 격리, 의도된 풀이 경로 및 최종 제출의 회귀검사 범위를 기록한다. 이는 이번 독립 참가자 관찰과 목적이 다르다.

특히 기존 문서에 기록된 07·08의 구현 풀이 검사는 의도된 동작이 유지되는지를 확인하는 자료다. 이번 07·08 검토는 정상 UX 범위이므로, 기존 회귀 성공을 가져와 “독립 검토자가 두 문제를 쉽게 풀었다” 또는 “힌트가 충분했다”고 결론 내리지 않는다. 반대로 이번 독립 검토의 중단을 문제 구현의 실패로 해석하지도 않는다.

## 실제 학생 확인에서 기록할 항목

운영 대상과 비슷한 초심자와 기본 경험자를 구분해 동일한 문제 설명·순서·힌트 조건으로 관찰하면, 이번 검토가 다루지 못한 부분을 확인할 수 있다.

- 첫 화면에서 어떤 행동을 먼저 했는지, 조사 방향을 정하지 못한 지점이 어디인지.
- 소스 보기와 개발자 도구를 스스로 시작했는지, 공통 도구 안내가 필요한지.
- 어느 힌트에서 진행이 다시 시작됐는지, 이미 수행한 행동을 반복하게 하는 힌트가 있었는지.
- 04에서 실제 상태 조작을 했는지, 06에서 공개 자료의 의미를 이해했는지.
- 05·06의 연결과 제출 결과의 문제 번호를 이해했는지.
- 부분 확인 후 값을 어떻게 보관하고, 마지막 완료 조건을 어떻게 이해했는지.

사람의 소요 시간과 성공률은 이런 관찰을 실제로 수행한 뒤 별도로 집계한다. 현재 보고서에는 그러한 수치를 제시하지 않는다.
