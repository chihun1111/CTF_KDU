공개 저장소의 플랫폼, 문제 서비스, 프런트엔드, 검증 도구와 컨테이너 구성을 대상으로

추가 확인했습니다. 단위/회귀 검사는 실제 HTTP 서버와 SQLite CLI를 포함하지만,
PostgreSQL·Redis·Nginx를 결합한 전체 배포 리허설을 대신하지 않습니다.

GitHub Actions의 `CI`는 공개 clone의 테스트·빌드·타입·민감 자료·전체 의존성을,
`Runtime integration`은 임시 secret과 일회성 Docker 스택에서 가입·로그인, 8개 문제,
사용자 격리, 관리자 기능, 최종 제출·1회용 인증을 검사하도록 구성했습니다. 워크플로
추가와 실제 실행 성공 여부는 구분하며, 실행 결과는 해당 커밋의 Actions 상태를 확인합니다.

첫 원격 실행에서 일반 CI는 모두 통과했고 Docker 이미지 빌드·13개 서비스 기동도
성공했습니다. 사용자 흐름 검사 중 Node fetch가 자동 전송하는 `Sec-Fetch-Mode: cors`와
클리어 화면의 탐색 보호 규칙이 충돌하는 점을 확인했습니다. 보호 규칙은 유지하고 smoke의
GET `/clear`만 실제 최상위 탐색 메타데이터를 보내도록 수정했으며, 실제 로컬 HTTP
전송 회귀 테스트 5개를 추가했습니다. 네 가지 smoke 흐름은 독립 단계로 실행해 어느
한 흐름이 실패해도 다른 흐름의 검증 결과를 함께 확인할 수 있습니다.

## 남은 운영 결정과 한계

1. 이 작업 환경에는 Docker daemon이 없습니다. 실제 배포 환경과 동일한 Compose 스택의
   성공 결과는 Docker가 있는 환경 또는 GitHub Actions 실행에서 확인해야 합니다.
2. TLS 인증서·외부 프록시·정확한 공개 도메인·프록시 IP 신뢰 범위는 운영 환경에서 설정합니다.
3. 속도 제한과 문제 08 grant는 단일 프로세스 상태입니다. 다중 복제본은 공유 저장소/세션
   고정 정책이 필요합니다. 예상 동시 참가자 수에 대한 부하 시험은 별도로 수행해야 합니다.
4. 문제 07 SQLite 파일의 자동 TTL 청소, 개인정보 보존·파기, 테스트 계정 정리, 백업 보관
   위치는 운영 정책으로 확정해야 합니다.
5. 기존 bcrypt 비밀번호는 호환성을 유지하므로 72바이트 절단 한계도 기존 계정에 남습니다.
   비밀번호 교체 UI 및 안전한 복구 절차는 추가 설계가 필요합니다.
6. 데이터베이스 migration은 최초 스키마 초기화 방식입니다. 이후 스키마 변경을 누적하려면
   migration 버전 이력과 복구 전략을 도입해야 합니다. 이번 보강은 스키마를 변경하지 않습니다.
7. file secret 소유권 때문에 backend와 일부 문제 서비스의 root 실행을 유지했습니다.
   capability를 제한했으며, 전체 비특권 전환은 UID/ACL 운영 방식 정리가 선행되어야 합니다.
8. 실제 학교의 참가 자격 확인·본인 확인·운영자 생성과 개인정보 안내 문구는 임의로 정하지
   않았습니다. 현재 공개 회원가입은 입력 형식과 중복만 검사합니다.

실제 운영 데이터·계정·도메인에는 변경을 적용하지 않았습니다. 병합과 배포는 브랜치의
검증 결과를 확인한 뒤 운영 환경에서 진행합니다.
